# 软件项目经理知识库与面试实战手册

> 适用方向：软件项目经理、技术项目经理、研发项目经理、游戏项目管理
> 目标：将已有的研发经验转化为系统化的项目管理能力，并能够在面试中用专业、结构化的方式表达。

---

# 一、项目经理的核心认知

## 1.1 项目经理到底负责什么

项目经理不是简单地“催进度”，也不是替所有人完成工作。

项目经理负责在有限的时间、资源、成本和质量约束下，让项目持续向目标推进，并最终完成交付。

项目管理的基本链路：

```text
目标
 ↓
范围
 ↓
计划
 ↓
资源
 ↓
风险
 ↓
沟通
 ↓
执行
 ↓
交付
 ↓
复盘
```

项目经理真正管理的是项目系统，而不是单个任务。

| 管理维度 | 核心问题              | 主要产出     |
| ---- | ----------------- | -------- |
| 目标管理 | 为什么做这个项目？成功标准是什么？ | 项目目标     |
| 范围管理 | 做什么？不做什么？         | 项目范围     |
| 计划管理 | 什么时间完成什么事情？       | 项目计划     |
| 任务管理 | 谁负责什么？            | WBS、任务清单 |
| 进度管理 | 当前是否按计划推进？        | 进度报告     |
| 风险管理 | 哪些事情可能导致失败？       | 风险登记表    |
| 资源管理 | 人力、设备、预算是否足够？     | 资源计划     |
| 沟通管理 | 谁需要知道什么？          | 沟通机制     |
| 质量管理 | 如何判断交付物合格？        | 验收标准     |
| 交付管理 | 如何完成上线或移交？        | 发布计划     |
| 复盘管理 | 为什么成功或失败？         | 复盘报告     |

---

## 1.2 项目经理与产品经理的区别

最容易记忆的区分方式：

| 角色    | 核心问题               |
| ----- | ------------------ |
| 产品经理  | 做什么？为什么做？为谁做？      |
| 项目经理  | 谁来做？什么时候做？如何保证做出来？ |
| 技术负责人 | 技术上怎么做？方案是否可行？     |
| 运营人员  | 上线后如何推广、运营和持续增长？   |

实际公司中职责可能重叠，但关注点不同。

### 项目生命周期

```text
立项
 ↓
需求分析
 ↓
产品设计
 ↓
技术设计
 ↓
任务拆解
 ↓
开发
 ↓
测试
 ↓
发布
 ↓
运营
 ↓
复盘
```

项目经理通常贯穿整个生命周期。

```text
│
├── 项目管理能力
│   ├── 项目计划
│   ├── 任务拆解
│   ├── 进度管理
│   ├── 风险管理
│   ├── 资源管理
│   ├── 质量管理
│   └── 成本管理
│
├── 技术理解能力
│   ├── 软件架构
│   ├── 开发流程

│   ├── CI/CD
│   ├── 测试
```

## 2.2 技能优先级

对于研发转项目经理，不建议一开始平均学习所有知识。

| 优先级 | 能力    | 原因             |
| --- | ----- | -------------- |
| S 级 | 项目规划  | 决定是否能把项目拆开     |
| S 级 | 任务拆解  | 决定计划是否可执行      |
| S 级 | 风险管理  | 决定能否提前发现问题     |
| S 级 | 进度管理  | 决定项目能否按期交付     |
| S 级 | 沟通协调  | 决定跨团队能否协作      |
| A 级 | 需求管理  | 控制范围蔓延         |
| A 级 | 质量管理  | 保证交付质量         |
| A 级 | 项目复盘  | 将经验沉淀为组织能力     |
| A 级 | 资源协调  | 解决人力和能力不足      |
| B 级 | 成本管理  | 正式项目中逐步补充      |
| B 级 | 供应商管理 | 外包、采购项目需要      |
| C 级 | 理论体系  | PMP 术语不应替代实战能力 |

核心原则：

> 不要为了面试背项目管理名词，而要学会如何把一个项目从 0 推到 1。

# 三、项目规划

## 3.1 拿到新项目后的第一步

不要直接开始拆任务。

先确认项目背景和基本约束。

| 确认内容 | 关键问题              |
| ---- | ----------------- |
| 项目背景 | 为什么要做？解决什么问题？     |
| 项目目标 | 最终要达到什么结果？        |
| 项目范围 | 哪些内容必须做？哪些不做？     |
| 时间要求 | 什么时候必须完成？         |
| 资源情况 | 有多少程序、美术、测试、产品资源？ |
| 技术条件 | 是否存在技术验证或外部依赖？    |
| 质量要求 | 什么标准才算完成？         |
| 干系人  | 谁会影响项目？谁需要参与决策？   |

正确顺序：

```text
确认背景
 ↓
明确目标
 ↓
确认范围
 ↓
识别约束
 ↓
组织团队分析
 ↓
任务拆解
 ↓
评估工作量
 ↓
制定计划
```

# 四、WBS：工作分解结构

## 4.1 什么是 WBS

WBS，全称 Work Breakdown Structure，即工作分解结构。

它不是简单的任务列表，而是：

> 将项目目标逐层拆解成可管理、可估算、可分配、可验收的工作单元。

例如：

```text
AI 陪伴宠物项目
│
├── 产品规划
│   ├── 用户画像
│   ├── 核心功能定义
│   └── MVP 范围确认
│
├── AI 能力
│   ├── 对话系统
│   ├── 语音输入
│   ├── 语音输出
│   └── 长期记忆
│
├── 宠物表现
│   ├── 情绪系统
│   ├── 表情系统
│   └── 动画系统
│
├── 设备端
│   ├── 硬件接入
│   ├── 网络通信
│   ├── 显示系统
│   └── OTA
│
├── 测试发布
│   ├── 功能测试
│   ├── 性能测试
│   ├── 稳定性测试
│   └── 发布上线
│
└── 运营复盘
    ├── 用户反馈
    ├── 数据统计
    └── 问题复盘
```

---

## 4.2 WBS 的拆解原则

### 原则一：按交付结果拆解

不要按照“某个人每天做什么”拆。

应该按照项目最终需要交付的结果拆。

| 不好的拆法   | 更好的拆法      |
| ------- | ---------- |
| 小王写代码   | 完成对话模块     |
| 小李调接口   | 完成 AI 服务接入 |
| 小张修 Bug | 完成语音链路稳定性  |
| 做一下测试   | 完成核心功能验收   |

---

### 原则二：每个阶段有明确目标

| 阶段   | 目标        |
| ---- | --------- |
| 需求阶段 | 明确要做什么    |
| 设计阶段 | 明确如何实现    |
| 开发阶段 | 完成功能实现    |
| 测试阶段 | 确认功能和质量达标 |
| 发布阶段 | 完成上线和交付   |

---

### 原则三：任务必须可估算

一个任务如果无法估算，通常说明拆得还不够细。

例如：

```text
完成 AI 系统
```

这个任务太大。

可以拆成：

```text
确认 AI 服务协议
 ↓
完成请求封装
 ↓
完成响应解析
 ↓
完成异常处理
 ↓
完成超时重试
 ↓
完成设备端联调
 ↓
完成测试
```

---

### 原则四：任务必须可验收

每个任务都应该能够回答：

> 什么条件下，才算完成？

例如：

| 任务     | 验收标准              |
| ------ | ----------------- |
| 对话接口接入 | 能够成功发送请求并获得回复     |
| 语音播放   | 音频能够正常播放且无明显卡顿    |
| 情绪系统   | 输入不同情绪事件后状态能够正确变化 |
| OTA    | 设备能够完成升级并恢复运行     |

---

## 4.3 WBS 的任务粒度

任务不能过大，也不能无限细化。

| 任务状态 | 问题            |
| ---- | ------------- |
| 过大   | 无法估算，延期原因不清晰  |
| 过小   | 管理成本过高，失去重点   |
| 合适   | 能够估算、分配、跟踪和验收 |

判断标准：

> 一个任务最好能够由明确负责人在相对短的周期内完成，并且具有独立的完成标准。

---

## 4.4 WBS 练习路径

| 阶段     | 目标                    |
| ------ | --------------------- |
| 1～2 周  | 掌握基本拆解方法，能够通过 PM 基础面试 |
| 1～2 个月 | 建立稳定的任务拆解能力           |
| 3～6 个月 | 通过真实项目形成项目管理肌肉记忆      |

最有效的方式不是单独背 WBS，而是拿真实项目练习。

# 五、项目计划与排期

## 5.1 制定项目计划的基本流程

```text
项目目标
 ↓
范围确认
 ↓
WBS 拆解
 ↓
工作量估算
 ↓
任务依赖分析
 ↓
资源分配
 ↓
关键路径识别
 ↓
风险预留
 ↓
形成排期
 ↓
与团队确认
```

---

## 5.2 工作量估算

不要直接拍脑袋估算。

建议采用：

```text
历史数据
   +
研发人员估算
   +
技术负责人校准
   +
任务依赖分析
   +
风险缓冲
```

示例：

| 工作内容 |   理论工作量 |
| ---- | ------: |
| 需求分析 |     1 天 |
| 技术设计 |     2 天 |
| 核心开发 |     5 天 |
| 联调   |     2 天 |
| 测试修复 |     3 天 |
| 发布准备 |     1 天 |
| 合计   | 14 个工作日 |

注意：

> 14 个工作日不等于 14 个自然日。

因为还存在会议、Code Review、Bug、依赖等待、临时需求和并行任务。

---

## 5.3 估算不是承诺

更准确的表达：

> 估算是基于当前信息对未来工作量的预测，不是绝对承诺。项目经理需要随着信息变化不断更新预测。

程序员说三天，最后变成七天，可能来自：

| 原因     | 说明             |
| ------ | -------------- |
| 技术不确定性 | 预估时不了解实际复杂度    |
| 任务拆解不足 | 隐藏工作没有被识别      |
| 依赖阻塞   | 等待其他团队或外部服务    |
| 需求变化   | 原始范围发生变化       |
| 质量问题   | 开发完成后发现大量缺陷    |
| 资源中断   | 临时会议、人员调动、并行任务 |
| 估算偏差   | 个人经验不足或过度乐观    |

PM 不应只问：

> 为什么你没按时完成？

更应该问：

> 哪些因素导致估算失真？以后如何提高预测准确性？

---

# 六、任务依赖与关键路径

## 6.1 什么是任务依赖

任务依赖是指：

> 一个任务的开始或完成，需要另一个任务先完成或提供条件。

例如：

```text
服务器 API
     ↓
客户端接入
     ↓
客户端与服务器联调
     ↓
测试
     ↓
发布
```

依赖关系会直接影响排期。

---

## 6.2 常见依赖类型

| 类型    | 含义             |
| ----- | -------------- |
| 完成—开始 | A 完成后，B 才能开始   |
| 开始—开始 | A 开始后，B 才能开始   |
| 完成—完成 | A 完成后，B 才能完成   |
| 外部依赖  | 依赖第三方、供应商或其他团队 |
| 资源依赖  | 需要特定人员或设备      |
| 技术依赖  | 必须先完成底层能力      |

---

## 6.3 什么是关键路径

Critical Path，关键路径，是决定项目最短完成时间的一系列任务链。

关键特点：

> 关键路径上的任务一旦延期，项目整体通常会受到影响。

例如：

```text
A → B → C → D
         \
          E
```

假设：

| 任务 |  工期 |
| -- | --: |
| A  | 2 天 |
| B  | 3 天 |
| C  | 5 天 |
| D  | 2 天 |
| E  | 1 天 |

主路径：

```text
A → B → C → D = 12 天
```

另一条路径：

```text
A → B → C → E = 11 天
```

如果 E 延期两天，可能不影响最终交付；如果 D 延期两天，则项目可能延期。

所以项目经理不能平均关注所有任务，而应重点关注：

```text
关键路径
关键依赖
高风险任务
阻塞任务
```

# 七、项目进度管理

## 7.1 如何判断项目是否健康

不能只看：

> 完成了多少任务。

应该从多个维度判断。

| 维度 | 关注指标                 |
| -- | -------------------- |
| 进度 | 计划完成率、实际完成率、延期任务数量   |
| 范围 | 新增需求数量、需求变更率         |
| 质量 | Bug 数量、P0/P1 Bug、回归率 |
| 风险 | 高风险数量、风险趋势、阻塞任务      |
| 资源 | 人员缺口、关键成员负载          |
| 成本 | 预算使用情况、资源成本          |
| 技术 | 性能指标、Crash、稳定性       |
| 交付 | 里程碑达成情况、上线准备度        |

可以使用项目健康度：

| 状态     | 含义                 |
| ------ | ------------------ |
| 🟢 正常  | 目标、进度、资源、质量基本符合计划  |
| 🟡 有风险 | 存在可能影响交付的问题，需要持续跟踪 |
| 🔴 已偏离 | 已经影响计划或目标，需要采取恢复措施 |

---

## 7.2 延期处理流程

项目延期不能第一时间等同于加班。

标准流程：

```text
识别延期
 ↓
确认延期事实
 ↓
定位根因
 ↓
评估影响范围
 ↓
确认关键路径
 ↓
评估剩余工作
 ↓
制定恢复方案
 ↓
重新排期
 ↓
同步干系人
 ↓
持续跟踪
 ↓
项目复盘
```

---

## 7.3 延期原因分类

| 类型   | 典型原因               |
| ---- | ------------------ |
| 需求问题 | 需求频繁变化、范围不清晰       |
| 技术问题 | 技术方案不成熟、技术难度超预期    |
| 资源问题 | 人员不足、核心成员离职        |
| 依赖问题 | 第三方 API、服务器、其他团队延期 |
| 估算问题 | 工作量评估不准确           |
| 管理问题 | 风险识别不足、信息同步滞后      |
| 质量问题 | Bug 数量过多、返工严重      |

---

## 7.4 延期后的解决方案

常见恢复手段：

| 方案     | 适用情况      | 风险        |
| ------ | --------- | --------- |
| 缩减范围   | 非核心需求较多   | 产品价值可能下降  |
| 增加资源   | 有明确资源缺口   | 新人需要学习成本  |
| 并行开发   | 任务之间可以并行  | 协作复杂度增加   |
| 优化技术方案 | 原方案效率低    | 可能引入技术风险  |
| 调整发布时间 | 时间可协商     | 商业或客户压力   |
| 分阶段发布  | 核心功能先上线   | 后续维护成本增加  |
| 加班冲刺   | 临近交付且任务可控 | 长期损耗团队稳定性 |

更成熟的表达：

> 我会先确认延期的真实原因和对关键路径的影响，再根据时间、范围、资源、质量四个维度制定恢复方案，而不是默认通过加班解决问题。

# 八、风险管理

## 8.1 风险与问题的区别

| 概念     | 定义              | 示例            |
| ------ | --------------- | ------------- |
| Risk   | 尚未发生，但未来可能发生的风险 | AI 接口可能延期     |
| Issue  | 已经发生，需要处理的问题    | AI 接口已经延期     |
| Action | 为解决问题而采取的行动     | 安排技术负责人重新评估方案 |

记忆方式：

```text
风险 = 未来可能发生
问题 = 已经发生
```

---

## 8.2 风险管理流程

```text
识别
 ↓
分析
 ↓
评估
 ↓
制定应对措施
 ↓
指定负责人
 ↓
设定时间节点
 ↓
持续监控
```

风险登记表：

| 风险         | 概率 | 影响 | 等级 | 应对措施           | 负责人   |
| ---------- | -- | -- | -- | -------------- | ----- |
| 第三方 API 延期 | 中  | 高  | 高  | 提前确认接口，准备 Mock | 技术负责人 |
| 核心成员离职     | 低  | 高  | 高  | 文档化、知识备份       | PM    |
| 性能不达标      | 中  | 高  | 高  | 提前进行性能验证       | 技术负责人 |
| 需求频繁变更     | 高  | 中  | 高  | 建立变更评审机制       | 产品/PM |
| 测试资源不足     | 中  | 中  | 中  | 提前锁定测试资源       | PM    |

---

## 8.3 风险应对策略

| 策略 | 含义            |
| -- | ------------- |
| 规避 | 改变方案，使风险不再存在  |
| 降低 | 降低发生概率或影响     |
| 转移 | 将风险转交给第三方或供应商 |
| 接受 | 风险可控，准备应急方案   |

例如：

### 技术风险

```text
核心技术没有验证
 ↓
先做技术预研
 ↓
制作最小可行 Demo
 ↓
验证性能与稳定性
 ↓
再进入正式开发
```

---

## 8.4 优秀 PM 与普通 PM 的区别

普通 PM：

> 发生问题后处理问题。

优秀 PM：

> 在问题发生前识别风险，并建立提前验证机制。

例如：

```text
第一次项目：
上线前才发现性能不达标

复盘：
为什么这么晚才发现？

根因：
没有性能测试节点

机制改进：
以后所有类似项目必须在 Beta 阶段进行性能测试
```

经验沉淀过程：

```text
个人经验
 ↓
项目经验
 ↓
团队流程
 ↓
组织资产
```

# 九、需求与范围管理

## 9.1 需求管理为什么重要

需求处理不好，通常会成为项目延期的重要原因。

项目经理需要管理：

| 事项   | 目标      |
| ---- | ------- |
| 需求收集 | 确认需求来源  |
| 需求澄清 | 消除歧义    |
| 需求分类 | 明确优先级   |
| 范围确认 | 确定版本归属  |
| 需求评估 | 判断成本和影响 |
| 变更管理 | 控制范围蔓延  |
| 验收确认 | 确认最终结果  |

---

## 9.2 需求优先级

可以使用重要—紧急四象限。

| 分类     | 处理方式        |
| ------ | ----------- |
| 重要且紧急  | 优先处理        |
| 重要不紧急  | 纳入计划        |
| 不重要但紧急 | 评估是否可以委派或简化 |
| 不重要不紧急 | 延后或放入待办池    |

但实际软件项目还应结合：

* 用户价值；
* 商业价值；
* 技术成本；
* 风险；
* 版本时间；
* 依赖关系。

---

## 9.3 需求变更流程

需求不是不能变，而是不能无成本地变。

推荐流程：

```text
提出变更
 ↓
澄清变更内容
 ↓
评估影响
 ↓
评估时间、资源、成本
 ↓
判断优先级
 ↓
产品、技术、项目共同确认
 ↓
更新计划
 ↓
同步相关人员
 ↓
执行与跟踪
```

---

## 9.4 需求变更时的核心问题

| 问题        | 目的        |
| --------- | --------- |
| 为什么必须变更？  | 判断真实价值    |
| 是否影响当前版本？ | 控制范围      |
| 增加多少工作量？  | 评估成本      |
| 是否影响关键路径？ | 判断延期风险    |
| 是否可以后置？   | 保持交付节奏    |
| 是否可以简化？   | 寻找 MVP 方案 |
| 谁批准变更？    | 明确决策责任    |

---

# 十、MVP 与范围控制

## 10.1 什么是 MVP

MVP，全称 Minimum Viable Product，即最小可行产品。

它不是“随便做一个简陋版本”，而是：

> 用最小的功能范围验证核心价值。

例如 AI 陪伴宠物项目：

完整版本：

```text
对话
语音
长期记忆
情绪系统
表情
动画
用户画像
数据统计
```

MVP 可以先做：

| 功能   | MVP 是否纳入 |
| ---- | -------- |
| 基础对话 | 是        |
| 语音输入 | 是        |
| 语音输出 | 是        |
| 基础情绪 | 是        |
| 长期记忆 | 可后置      |
| 复杂动画 | 可后置      |
| 用户画像 | 可后置      |
| 数据统计 | 可后置      |

核心原则：

> 先验证核心价值，再扩展非核心功能。

---

## 10.2 MoSCoW 优先级

| 等级          | 含义        |
| ----------- | --------- |
| Must have   | 必须有       |
| Should have | 应该有       |
| Could have  | 有最好，但不是必须 |
| Won't have  | 当前版本不做    |

---

# 十一、质量管理

## 11.1 质量不是测试阶段才开始

质量管理应该贯穿项目全过程。

```text
需求质量
 ↓
设计质量
 ↓
开发质量
 ↓
测试质量
 ↓
发布质量
 ↓
运行质量
```

---

## 11.2 软件项目质量指标

| 阶段  | 指标                   |
| --- | -------------------- |
| 需求  | 需求澄清率、变更率            |
| 开发  | Code Review 完成率、静态检查 |
| 测试  | Bug 数量、严重程度          |
| 稳定性 | Crash 率、异常率          |
| 性能  | CPU、内存、帧率、响应时间       |
| 发布  | 发布成功率、回滚次数           |
| 线上  | 用户反馈、故障数量            |

---

## 11.3 P0 / P1 / P2 Bug

具体等级以公司定义为准，但通常可以理解为：

| 等级 | 含义            | 处理方式     |
| -- | ------------- | -------- |
| P0 | 阻断核心流程或严重线上事故 | 立即处理     |
| P1 | 严重影响主要功能      | 发布前必须解决  |
| P2 | 一般功能问题        | 根据版本安排修复 |
| P3 | 轻微问题或体验优化     | 排期处理     |

如果测试发现大量 P1 Bug，而上线时间已到：

```text
确认 Bug 真实数量
 ↓
按严重程度分类
 ↓
判断是否影响核心流程
 ↓
确认是否存在临时规避方案
 ↓
评估发布风险
 ↓
向决策者提供上线/延期方案
```

项目经理不能为了满足日期而隐瞒质量风险。

---

# 十二、团队沟通与冲突管理

## 12.1 项目经理有没有权力要求程序员做事

项目经理通常不一定拥有行政管理权。

因此项目推进不能只依靠：

> “我是项目经理，你必须听我的。”

更有效的方式是：

```text
明确目标
 ↓
理解原因
 ↓
讨论方案
 ↓
明确责任
 ↓
达成共识
 ↓
持续跟踪
```

核心能力：

> 用机制、信息、目标和影响力推动团队，而不是只依赖职位权力。

---

## 12.2 程序员不配合怎么办

不要直接给人贴标签。

分析顺序：

| 方向 | 需要确认的问题      |
| -- | ------------ |
| 目标 | 是否理解项目目标？    |
| 任务 | 是否明确具体工作？    |
| 资源 | 是否存在资源不足？    |
| 技术 | 是否遇到无法解决的问题？ |
| 排期 | 是否认为时间不合理？   |
| 动机 | 是否存在沟通或管理问题？ |

处理流程：

```text
了解原因
 ↓
确认事实
 ↓
明确目标和责任
 ↓
提供支持
 ↓
制定行动计划
 ↓
持续跟踪
 ↓
必要时升级
```

---

## 12.3 产品和研发发生冲突怎么办

典型场景：

```text
产品：下周必须上线
研发：至少需要一个月
```

项目经理不应直接站队。

应该把争论转化为可比较的方案。

| 方案 | 范围          |   时间 | 资源要求 | 风险 |
| -- | ----------- | ---: | ---- | -- |
| A  | 完整功能        | 30 天 | 当前资源 | 低  |
| B  | 核心功能        | 10 天 | 当前资源 | 中  |
| C  | 核心功能 + 增加资源 |  7 天 | 额外资源 | 中高 |

PM 的职责不是替产品或研发做决定，而是：

1. 澄清目标；
2. 收集事实；
3. 评估影响；
4. 提供可执行方案；
5. 推动决策。

---

## 12.4 两个团队互相甩锅怎么办

不要先判断谁对谁错。

建立问题事实链：

```text
问题发生在哪里？
 ↓
哪个任务受到影响？
 ↓
前置条件是什么？
 ↓
谁负责提供条件？
 ↓
当前阻塞点是什么？
 ↓
下一步谁负责解决？
 ↓
什么时间完成？
```

将“责任争论”转换成：

> 当前问题、影响范围、解决方案、负责人、截止时间。

---

## 12.5 团队成员能力不足怎么办

正确流程：

```text
发现能力问题
 ↓
确认具体差距
 ↓
沟通原因
 ↓
明确岗位预期
 ↓
提供培训或支持
 ↓
设定改善目标
 ↓
观察周期
 ↓
仍未改善时采取正式绩效措施
```

PIP 不是惩罚工具，而是绩效改善工具。

---

# 十三、项目会议与汇报

## 13.1 如何召开有效会议

会议不是为了让所有人轮流汇报。

会前：

| 工作     | 目的     |
| ------ | ------ |
| 收集进度   | 提前了解状态 |
| 收集问题   | 提前识别阻塞 |
| 明确会议目标 | 避免无效讨论 |
| 准备数据   | 减少主观争论 |

会议中：

```text
当前目标
 ↓
完成情况
 ↓
未完成事项
 ↓
阻塞问题
 ↓
解决方案
 ↓
责任人
 ↓
截止时间
```

会后：

* 记录决策；
* 更新任务；
* 明确负责人；
* 跟踪行动项。

---

## 13.2 如何向老板汇报项目

老板通常不关心所有技术细节，而更关心项目是否还能按时交付。

推荐汇报结构：

| 顺序 | 内容        |
| -- | --------- |
| 1  | 当前项目状态    |
| 2  | 原定目标      |
| 3  | 已完成情况     |
| 4  | 当前风险      |
| 5  | 已发生问题     |
| 6  | 解决方案      |
| 7  | 需要老板决策的事项 |

示例：

> 当前项目整体完成率约为 70%，核心功能已完成，但服务器联调存在延期风险。按照当前资源预计 9 月 30 日可能无法完成全部功能。我们准备了三个方案：维持完整范围延期 7 天、缩减非核心功能按期上线、增加资源压缩关键路径。希望确认最终交付策略。

# 十四、项目复盘

## 14.1 复盘不是追责大会

低质量复盘：

> 谁导致了问题？

高质量复盘：

> 为什么这个问题会发生？为什么没有提前发现？以后如何避免？

标准流程：

```text
目标
 ↓
实际结果
 ↓
偏差
 ↓
原因分析
 ↓
机制问题
 ↓
改进措施
 ↓
责任人
 ↓
完成时间
 ↓
验证效果
```

---

## 14.2 复盘问题模板

| 方向 | 问题             |
| -- | -------------- |
| 目标 | 项目目标是否明确？      |
| 范围 | 是否出现范围蔓延？      |
| 计划 | 排期是否合理？        |
| 估算 | 哪些任务估算不准确？     |
| 风险 | 哪些风险没有提前识别？    |
| 资源 | 是否存在人员不足或依赖阻塞？ |
| 沟通 | 信息是否同步及时？      |
| 质量 | 哪些问题本应提前发现？    |
| 决策 | 是否存在决策延迟？      |
| 流程 | 哪些机制需要改进？      |

# 十五、敏捷开发基础

## 15.1 Scrum 与 Kanban

| 维度   | Scrum       | Kanban        |
| ---- | ----------- | ------------- |
| 核心思想 | 固定周期迭代      | 持续流动交付        |
| 时间方式 | Sprint      | 不要求固定周期       |
| 任务管理 | Backlog     | 看板工作流         |
| 工作限制 | Sprint 范围   | WIP 限制        |
| 适合场景 | 需求相对稳定、迭代明确 | 需求持续变化、任务流动频繁 |

---

## 15.2 Kanban

Kanban 的核心：

```text
可视化工作流
      +
限制 WIP
      +
持续交付
```

示例：

```text
Todo
 ↓
Doing
 ↓
Review
 ↓
Testing
 ↓
Done
```

WIP 即 Work In Progress，正在进行中的任务数量。

例如：

> Doing 阶段最多同时存在 3 个任务。

这样可以减少任务堆积和频繁切换。

---

## 15.3 Scrum

Scrum 的典型流程：

```text
Product Backlog
       ↓
Sprint Planning
       ↓
Sprint
       ↓
Daily Scrum
       ↓
Sprint Review
       ↓
Retrospective
       ↓
下一轮 Sprint
```

核心概念：

| 概念              | 含义              |
| --------------- | --------------- |
| Product Backlog | 所有待完成工作的集合      |
| Sprint          | 固定周期的开发迭代       |
| Sprint Planning | 确定本轮 Sprint 做什么 |
| Daily Scrum     | 同步进度、问题和计划      |
| Sprint Review   | 展示本轮成果          |
| Retrospective   | 复盘过程并改进         |

---

## 15.4 Backlog

例如 AI 陪伴宠物项目：

| Backlog 项目 | 优先级 |
| ---------- | --- |
| 对话系统       | 高   |
| 语音输入       | 高   |
| 语音输出       | 高   |
| 基础情绪       | 高   |
| 长期记忆       | 中   |
| 表情系统       | 中   |
| 动画系统       | 中   |
| 用户画像       | 低   |
| 数据统计       | 低   |

Sprint Planning 时，从 Product Backlog 中选择当前周期能够完成的任务。

# 十六、RACI 责任矩阵

RACI 用于明确跨团队项目中的责任。

| 字母 | 含义          | 说明        |
| -- | ----------- | --------- |
| R  | Responsible | 实际执行工作的人  |
| A  | Accountable | 对最终结果负责的人 |
| C  | Consulted   | 需要被咨询的人   |
| I  | Informed    | 需要被通知的人   |

最重要的区别：

> R 是干活的人，A 是最终负责的人。

示例：AI 对话功能上线。

| 角色     | RACI |
| ------ | ---- |
| 项目经理   | A    |
| AI 程序员 | R    |
| 产品经理   | C    |
| 测试人员   | R    |
| 老板     | I    |

注意：一个任务最好只有一个最终 A，避免责任模糊。

# 十九、AI 陪伴宠物项目实战案例

这是最适合研发转 PM 的核心案例。

不要只描述：

> 我做过一个 AI 陪伴宠物。

应该包装成完整项目。

---

## 19.1 项目背景

项目目标：

开发一款具备 AI 对话、情绪表达和实体交互能力的智能陪伴宠物。

项目涉及多个技术方向：

| 模块  | 内容            |
| --- | ------------- |
| AI  | 对话、语音、记忆      |
| 嵌入式 | ESP32-S3、设备通信 |
| UI  | LVGL、表情显示     |
| 动画  | 表情和动作系统       |
| 网络  | WebSocket、OTA |
| 硬件  | 显示、麦克风、扬声器    |
| 工程  | 构建、烧录、发布      |
| 测试  | 功能、稳定性、性能     |

---

## 19.2 项目目标

| 目标    | 结果定义          |
| ----- | ------------- |
| 对话能力  | 用户能够与宠物进行正常交互 |
| 语音能力  | 能够完成语音输入和输出   |
| 情绪表达  | 根据交互状态展示不同情绪  |
| 设备稳定性 | 长时间运行不出现严重崩溃  |
| 网络通信  | 能够稳定连接服务端     |
| 交付能力  | 完成可运行版本并进行测试  |

---

## 19.3 项目范围

### MVP 范围

| 功能     | 是否属于 MVP |
| ------ | -------- |
| 基础对话   | 是        |
| 语音输入   | 是        |
| 语音输出   | 是        |
| 基础情绪系统 | 是        |
| 基础表情显示 | 是        |
| OTA    | 是        |
| 长期记忆   | 后续版本     |
| 复杂动画   | 后续版本     |
| 用户画像   | 后续版本     |
| 数据统计   | 后续版本     |

---

## 19.4 WBS

```text
AI 陪伴宠物项目
```

# 二十二、重点面试题参考回答框架

## 22.1 你理解的软件项目经理是什么角色？

推荐回答：

> 我理解项目经理的核心职责，是在明确目标的前提下，负责项目整体规划、任务拆解、进度推进、风险识别、资源协调、跨部门沟通以及最终交付。项目经理不一定亲自完成所有任务，但需要建立机制，让团队能够在时间、范围、质量和资源约束下稳定推进项目。

---

## 22.2 项目经理需要懂技术吗？

推荐回答：

> 我认为项目经理不一定需要达到开发人员的编码水平，但技术项目经理必须具备足够的技术理解能力。这样才能听懂研发方案、识别技术风险、判断任务依赖，并在排期和资源协调时做出合理判断。我的研发背景能够帮助我理解技术问题，但我也会注意保持职责边界，不替技术负责人做具体技术决策。

---

## 22.3 什么是项目成功？

不要只回答“按时上线”。

项目成功至少包括：

| 维度 | 目标      |
| -- | ------- |
| 时间 | 按计划完成   |
| 范围 | 核心需求完成  |
| 成本 | 资源和预算可控 |
| 质量 | 满足验收标准  |
| 业务 | 达成项目目标  |
| 用户 | 提供实际价值  |

---

## 22.4 项目延期怎么办？

推荐结构：

```text
确认延期事实
 ↓
定位延期原因
 ↓
评估影响范围
 ↓
识别关键路径
 ↓
评估剩余工作
 ↓
制定恢复方案
 ↓
重新排期
 ↓
同步相关人员
 ↓
持续跟踪
 ↓
复盘改进
```

参考表达：

> 我不会第一时间要求团队加班，而是先确认延期来自需求变化、技术风险、资源不足、依赖阻塞还是估算偏差。然后判断是否影响关键路径，再结合范围、资源和时间制定恢复方案，例如缩减非核心需求、增加资源、调整技术方案或分阶段发布。最终形成明确的责任人和时间节点，并同步相关干系人。

---

## 22.5 如果研发不接受你的排期怎么办？

推荐回答：

> 我会先确认研发认为不合理的具体原因，是工作量估算、技术风险、资源不足还是依赖条件没有满足。然后和技术负责人一起重新拆解任务、评估工作量和关键路径。如果确实存在客观约束，我会调整计划；如果目标时间不可变，则提供缩减范围、增加资源或调整技术方案等选项，最后让相关决策者基于事实做选择。

---

## 22.6 为什么从开发转 PM？

建议结构：

```text
过去经历
 ↓
发现问题
 ↓
产生兴趣
 ↓
已有实践
 ↓
未来目标
```

参考表达：

> 我并不是突然从开发转向项目管理，而是在过去的研发经历中逐渐发现，项目最终能否顺利落地，不只是技术实现的问题，还取决于需求、计划、资源、沟通和风险管理。过去在项目中，我除了负责研发工作，也参与过任务推进、问题协调和版本交付。通过复盘这些经历，我发现自己对整体项目推进和团队协作有较强兴趣。因此我希望将已有的技术背景转化为技术理解能力和项目管理能力，成为能够理解研发、协调团队并对项目结果负责的人。

| 5  | 判断是否可以并行      |

| 7  | 评估增加资源的可能性    |

## 场景二：老板要求必须按时上线

条件：

```text
老板：9 月 30 日必须上线
产品：需求一个都不能砍
技术负责人：10 天就是 10 天
团队：已经满负荷
HR：不能调人
供应商：无法支援
```

### 错误回答

> 加班解决。

### 正确思路

先明确：

> 时间、范围、资源、质量四个条件同时不可变化时，项目经理无法通过管理技巧创造不存在的产能。

此时应：

1. 量化当前缺口；
2. 说明现状与目标之间的差距；
3. 明确技术和质量风险；
4. 提供最低可行的替代方案；
5. 让决策者确认优先级；
6. 对无法满足的约束进行正式升级。

成熟表达：

> 我会先把当前目标、剩余工作量、团队实际产能和关键风险量化出来。如果在现有约束下确实无法满足目标，我不会承诺一个无法实现的结果，而是明确说明差距和风险，并推动决策者确认哪些约束可以调整。项目经理的职责不是制造虚假的确定性，而是让决策建立在真实信息之上。

# 二十六、项目经理的核心思维升级

从开发转 PM，最重要的不是把技术能力丢掉，而是改变观察问题的层级。

| 开发思维        | PM 思维              |
| ----------- | ------------------ |
| 这个 Bug 怎么修？ | 为什么这个问题会发生？        |
| 我能不能自己解决？   | 谁最适合解决？            |
| 任务完成了吗？     | 项目目标是否受影响？         |
| 谁导致了延期？     | 为什么风险没有提前暴露？       |
| 产品说要做就做     | 需求变更的影响是什么？        |
| 研发说做不了      | 做不了的原因是什么？有没有替代方案？ |

| 项目结束了       | 如何沉淀经验避免重复问题？      |

真正的变化是：

> 从“解决问题”升级为“管理问题、风险和决策”。

# 二十八、最终训练目标

最终不是背出标准答案，而是形成以下反应模式：

当面试官问：

> 项目延期怎么办？

能够自动想到：

```text
延期事实
→ 原因
→ 影响
→ 关键路径
→ 资源
→ 范围
→ 时间
→ 质量
→ 方案
→ 决策
→ 跟踪
```

当面试官问：

> 研发不配合怎么办？

能够自动想到：

```text
原因
→ 目标
→ 任务
→ 资源
→ 沟通
→ 共识
→ 责任
→ 升级
```

当面试官问：

> 如何证明你适合 PM？

能够自动想到：

```text
真实项目经历
→ 实际承担职责
→ 解决的问题
→ 最终结果
→ 方法论沉淀
→ 可迁移能力
```

核心目标：

> 从“我做过项目”升级为“我理解项目如何被规划、推进、控制风险并最终交付”。
